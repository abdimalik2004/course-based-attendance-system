Course-Based Attendance System - Technical Documentation

1. Project Overview

Project name: Course-Based Attendance System

Main purpose: A role-based attendance management platform built to manage academic attendance by course and schedule, integrating face recognition for student presence validation.

Problems the system solves:
- Eliminates manual attendance marking and paper-based registers
- Supports course-level and session-level attendance tracking
- Enforces faculty-scoped access control
- Provides automated absence marking after sessions end
- Enables face-recognition based student validation

Main features and capabilities:
- JWT-based authentication with refresh token cookie flow
- Role-based access control (SUPER_ADMIN, ACADEMIA, FACULTY, FACULTY_ADMIN, HR, ADMISSIONS, TEACHER, STUDENT)
- CRUD APIs for faculties, departments, classes, courses, schedules, students, teachers
- Course assignment and schedule management
- Attendance session lifecycle: start / end / active session listing
- Face-frame attendance processing and duplicate prevention
- Attendance reports and record editing
- Dataset, model training, and recognition tooling in desktop modules
- Dockerized backend with MySQL support and health checks

System architecture type:
- Monolithic web application with modular separation
- FastAPI backend API + React frontend SPA + Python desktop/CLI tooling
- SQL database persistence via SQLAlchemy
- AI/ML face recognition pipeline for attendance validation

- `Teacher`: teacher profile linked to `User`
- `Course`: code, title, normalized title, schedules, assignments

7. Authentication & Authorization

Login system & token flow:
- `POST /auth/token` (form) issues access token and sets refresh token cookie
- `POST /auth/refresh` reads refresh cookie and issues new access token
- `GET /auth/me` returns user profile

Password hashing:
- Passlib with bcrypt; rehash if needed

Role-based access control:
- `require_roles` dependency enforces required roles
- `SUPER_ADMIN` bypasses faculty scoping
- Faculty equivalents: `FACULTY` and `FACULTY_ADMIN`

Protected routes and permissions:
- Many router endpoints include `Depends(require_roles(...))` and faculty scope checks


8. Attendance System Logic

Session creation:
- `POST /sessions/start` enforces single active session per course; teacher or admin can start

Student attendance tracking (frame flow):
- `POST /attendance/frame` receives base64 image
- Frame decoded and passed to face recognition; recognizer returns student number and confidence
- Validate student registration, faculty, enrollment, duplicate attendance
- Determine status using session.schedule.grace_period_minutes: PRESENT or LATE
- Create `AttendanceRecord` with confidence and timestamp

Session closure:
- `POST /sessions/end` ends session and `close_session_and_mark_absent()` creates `ABSENT` records for enrolled students without attendance records

AI/Recognition:
- `FaceService` loads models and calls `FaceEmbeddingRecognizer` to recognize frames
- Timeout and confidence threshold enforced via settings


9. API Documentation (concise)

Auth:
- POST /auth/token (form) -> { access_token }
- POST /auth/refresh -> { access_token } (reads cookie)
- GET /auth/me -> current user
- POST /auth/logout -> clears cookie

Sessions:
- POST /sessions/start { course_id, schedule_id?, session_type }
- POST /sessions/end { session_id }
- GET /sessions
- GET /sessions/active [filters]

Attendance:
- POST /attendance/frame { session_id, image }
- GET /attendance/records [filters]
- PUT /attendance/records/{record_id} { status }

Courses/Students/Other:
- Standard CRUD endpoints under `/courses`, `/students`, etc. with role protections

Error responses:
- 400/401/403/404/409/422/500 with JSON `_error_payload`


10. Frontend-Backend Integration

How frontend communicates with backend:
- `frontend/src/services/api.ts` axios instance with baseURL from `VITE_API_URL` and `withCredentials: true`
- Access token appended in `Authorization` header; refresh handled via cookie

Authentication handling:
- `authService` login/refresh/initialize/logout wrappers
- `useAuthStore` persists auth state

Error handling:
- Axios response interceptor refreshes on 401 and retries
- On failed refresh, logs out user and redirects to `/login`

14. System Workflow (step-by-step)

User login:
```bash
POST /auth/token (username/password form)
Store access token in frontend; refresh token set as httpOnly cookie
Call /auth/refresh then /auth/me to populate user state
```

Attendance taking:
1. Teacher starts session via `/sessions/start`
2. Frontend camera captures image and calls `/attendance/frame`
3. Backend recognizes student and creates `AttendanceRecord`
4. Teacher ends session `/sessions/end`; backend marks absences

Course assignment / schedule management:
- Faculty/Academia create schedules and assignments via `/courses` and schedule endpoints

Report generation:
- Frontend calls `/attendance/records` and other report endpoints; transforms and displays data

17. Current Project Status

Completed:
- Backend API and models implemented
- Auth, RBAC, attendance processing, and frontend SPA present
- Seed data and health checks implemented

Incomplete / concerns:
- `ScheduleService._tick()` is currently a stub and does not auto-manage sessions
- CORS and cookie config may need production tightening
- Model-loading and recognition scaling require architectural consideration


18. Recommendations

Performance:
- Implement scheduler automation
- Offload heavy recognition to worker processes or separate service

Security:
- Harden CORS, secure cookies, HTTPS enforcement, CSRF mitigation

Code quality:
- Add tests, linting, CI
- Normalize role names across frontend/backend

Scalability:
- Consider dedicated recognition microservice, model cache, or GPU-backed service


19. Final Summary

Overall evaluation:
- Strong, well-structured system with clear domain modeling and role-based controls
- Good integration of face recognition for attendance
- Main gaps: scheduler automation, production security hardening, and recognition scaling

Strengths:
- Clean modular codebase
- Modern frontend stack
- Seed data and health checks

Weaknesses:
- Scheduler disabled
- Some production security defaults are permissive

Complexity level: moderate-to-high

Professional assessment:
- System is close to production-ready for small deployments; requires scheduler and security improvements for broader production use.
